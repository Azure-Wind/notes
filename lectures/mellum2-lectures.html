00 · OVERVIEW

目标不是单纯做大模型，而是让代码模型能落地、能行动

笔者这次讲座基本上没听懂。以下以主讲人 PPT 为主，把内容按技术脉络重新整理；必要的概念解释是为了方便复习，不表示笔者已经完全掌握。

关于笔记范围：正文以 PPT 明确给出的内容与数字为主。手写笔记中已确认的两处信息——MTP 与 DeepSeek 的关联、约 90% 的条件准确率记录——放回对应技术部分；其他难以辨认的零散记录不再单独展开。

两个目标

01 · 做好 next-edit suggestion

为 IDE 场景提供便宜、快速、质量可靠的下一段代码编辑建议。这要求模型不仅输出质量好，还要控制单次延迟与并发吞吐。

02 · 尝试让模型具备 Agent 能力

从补全与问答延伸到多步软件工程任务：理解仓库、使用 shell / 文件工具、执行测试、根据反馈继续修改。

为什么要做 12B-A2.5B 的代码模型？

  • 产品场景：延迟、数据治理，以及尽可能高质量的代码补全。
  • 开放模型：研究在相同推理预算下，能否做出比 Qwen2.5 更合适的模型。
  • 研究用途：JetBrains 的多个实验室可以基于开放权重开展新场景实验。

01 · PRE-TRAINING ARCHITECTURE

架构选择：把总参数规模与每 token 计算量拆开

设计约束来自真实部署：在一张 H100、FP8 推理条件下，尽量匹配 Qwen2.5-7B 的延迟与吞吐，再在这个预算内比较不同架构的质量。

设计方法与基础配置

PPT 把目标使用形态描述为“长上下文输入、短编辑输出”，示例为约 2,304 个输入 token、256 个输出 token。团队比较 dense 与 MoE、专家激活数、KV heads、注意力机制和 MTP 等配置；对每个候选配置先画出相同延迟下的可行范围，再检查模型质量。

12B

总参数量

模型中存储的总参数规模，决定可承载的知识与专家容量上限。

2.5B

每 token 激活参数

MoE 每次只选择部分专家计算，因而每个 token 的计算量接近 2.5B dense 模型。

28 × 2,304

层数 × hidden width

PPT 展示的 Mellum 2 主要配置；在质量与延迟约束中选定。

Mixture of Experts（MoE）：每个 token 只调用部分专家

每个 MoE 层包含多个前馈网络专家（FFN），路由器根据当前 token 的表示选择一部分专家。Mellum 2 采用 64 个专家、每个 token 激活 8 个、没有额外共享专家。因此，总容量是 12B 参数，但单个 token 不需要经过全部参数。

  • 专家数增加会扩大模型容量，但也受 GPU 显存限制；团队将专家数定为 64。
  • 更少的激活专家通常速度更快；PPT 报告 2 个激活专家的延迟约比 8 个低 1.5 倍，但小规模模型的质量明显更差。
  • 最终选择 8/64，在模型质量、推理速度和总容量之间取平衡。加入始终激活的 shared expert 没带来可测的质量收益，却增加每 token 计算量，因此被删去。

Grouped-Query Attention（GQA）：减少 KV cache

自回归解码需要缓存之前 token 的 Key 和 Value。MHA 为每个 Query head 配一组 KV；MQA 让所有 Query heads 共享一组 KV；GQA 则介于两者之间，让一组 Query heads 共享一组 KV。

注意力形式KV 组织缓存相对规模（PPT 示意）主要取舍
MHA每个 Query head 独立 KV1×表达能力强，但缓存最大。
GQA多个 Query heads 共享 KV1/8（示意）质量接近 MHA，解码更省缓存。
MQA所有 Query heads 共用一组 KV1/32（示意）缓存最小，但质量可能下降。

模型有 32 个 Query heads；最终使用 4 个 KV heads，即每 8 个 Query heads 共用一个 KV head。PPT 提到，8 个 KV heads 对速度不够理想，而 2 个 KV heads 会损害质量，4 个是折中点。缓存越小，解码时需要搬运的数据越少；但共享程度越高，注意力的表达自由度也可能下降。

Sliding-Window Attention（SWA）：局部与全局层混用

局部滑动窗口层只关注当前位置之前最近的 W 个 token；全局层仍可访问所有先前 token。Mellum 2 按 3 个局部层配 1 个全局层的方式重复堆叠，窗口设置参考 Gemma 3。

  • 局部层：KV cache 不会随着全部上下文长度持续增长，prefill 的注意力成本也受窗口限制。
  • 全局层：保留较远 token 之间的信息通路，避免整个模型只看局部窗口。

这是结构上的折中：大部分层获得有界的局部注意力成本，同时通过周期性全局层保留长程信息。

QK-Norm：抑制注意力 logits 失控

QK-Norm 在计算 Query 与 Key 的点积之前，按注意力头对它们做 RMSNorm。没有归一化时，Query / Key 的幅度可能不断变大，使 attention logits 放大，softmax 逐渐变得近乎 one-hot，并引发 loss spike。归一化通过可学习的增益控制分数尺度，改善训练稳定性。PPT 说 Mellum 2 沿用了 Qwen3-MoE 风格解码器中的这一设计。

02 · MTP & MLA

MTP 是 DeepSeek 系列也采用的训练目标；MLA 则是权衡后没有选用的架构

这里把手写记录中确认的 MTP 与 90% accuracy 放回相关概念中，并补充 PPT 没展开讲清楚的 MLA 选型原因。

Multi-Token Prediction（MTP）：一个辅助头预测更后面的 token

普通自回归语言模型在每个位置主要学习预测下一个 token。MTP 再增加一个预测头，让同一位置同时对后续 token（例如 t+2）提供训练目标。这样一个位置就能给模型更密集的监督信号。这个思路并非 Mellum 独有：DeepSeek-V3 技术报告也采用了 MTP 训练目标，PPT 的引用中明确列出了 DeepSeek-V3。

共享 Transformer 主干读取 tokens 1…t，产生当前位置的 hidden state
→
主预测头学习预测下一个 token（t+1）
+
MTP 辅助头额外预测更后面的 token（例如 t+2）

Mellum 2 保留一个低权重的 MTP 头。PPT 报告的一次消融实验中，MMLU-Pro 提升 3.3、GSM8K 提升 3.0，MBPP 基本持平。推理时，辅助头还可作为 speculative decoding 的 draft：先提出候选 token，再由主模型验证，不需要另外部署一个独立草稿模型，因此设计目标是不额外增加服务成本。

手写笔记中的 accuracy：笔者记录到“在前一个 token 预测正确的条件下，后一个 token 的预测准确率约为 90%”。这里按你的补充保留为现场记录；PPT 本身没有给出这一数值的评测集、样本范围与统计定义，因此不能把它当作 MTP 的通用准确率，也不应与上述 MMLU-Pro / GSM8K 分数混为一谈。

Multi-head Latent Attention（MLA）：为什么 Mellum 2 最后没有采用？

MLA 的目标与 GQA 相似：降低长上下文解码时的 KV cache 成本，但方法不同。GQA 通过让多个 Query heads 共享 KV heads 来减少缓存；MLA 则把 Key / Value 的信息压缩到低秩 latent 向量中缓存，需要计算注意力时再利用投影关系恢复或吸收相应计算。MLA 能大幅压缩缓存，但会引入潜变量投影、额外计算以及对推理内核支持的要求。

这不是只靠通用原理推测的原因：Mellum 2 技术报告的架构消融附录专门报告了 MLA 实验。团队移除 MoE 层、换成 DeepSeek 风格 MLA 进行测试，结果是：

  • 速度约束下可扩到约 5.5B 参数：以当时 vLLM 后端唯一支持的 latent rank = 512 进行实验，MLA 架构能在大致匹配 Qwen2.5-7B 延迟的条件下做到约 5.5B 参数。
  • 质量收益不够：在既定延迟预算下，测试的 dense 配置没有稳定超过 Qwen2.5-7B 的评测质量基线；MLA 带来的质量提升不足以证明额外训练复杂度是值得的。
  • 模型规模不匹配：报告认为 rank 512 对 Mellum 2 所在的模型规模偏大，能带来的 KV-cache 压缩收益因此有限。
  • MoE 路线更符合目标：转向 MoE 后，总参数量可扩至约 12B，每 token 激活约 2.5B 参数，更适合在既定推理预算内增加模型容量。
结论：不是“MLA 一定比 GQA 差”，而是 Mellum 团队在当时的模型规模、vLLM 支持、硬件与延迟预算下，发现 MLA 的缓存优势没有转化成足够的质量—速度收益；MoE + GQA 更符合 IDE 场景的目标。若模型规模、后端内核或硬件变化，结论未必相同。
03 · DATA & LONG CONTEXT

约 10.65T tokens 的三阶段预训练，以及 128K 长上下文扩展

数据配方逐步从广泛网页语料转向更高比例的代码与数学内容；长上下文阶段还测试了位置外推与额外长文档数据的影响。

预训练数据与三阶段配比

整套预训练约使用 10.65T tokens。数据包括许可较宽松的代码仓库、Common Crawl 网页数据、合成改写内容和数学教材；技术报告提到数据与 Nemotron-CC、FineWeb 有关。训练使用 Muon 优化器，并贯穿 BF16/FP8 混合精度方案；代码采用 Fill-in-the-Middle（FIM）形式训练，使模型学习根据前后文填补中间内容。

长上下文：layer-selective YaRN

模型基础上下文为 8K，团队在长上下文 mid-training 阶段扩展到 128K（131,072 tokens）。用到的是 layer-selective YaRN：只在全局注意力层进行相应的位置缩放，方案参考 Gemma 3 与 OLMo 3，而不是所有层统一改变。

团队观察到，长上下文训练在某些指标已经趋于饱和后仍继续训练，目的是让 MoE router 在扩展上下文的环境中稳定下来。另一方面，加入 OLMo 3 的 Longmino（长科学 PDF 加合成任务）后，RULER 结果在各方案上都下降约 2–3 个百分点，说明更多长文档数据不一定自动带来更好的长上下文表现。

04 · FINE-TUNING

SFT 先教模型怎么回答，RLVR 再用可验证结果强化行为

Mellum 2 从同一长上下文基础模型分出 Instruct 与 Thinking 两条后训练路线，后续分别进行可验证奖励强化学习。

SFT · Supervised Fine-Tuning

用精选示范逐 token 模仿目标输出。重点是把模型调整到适合指令、对话、代码协作和工具调用的行为模式。

RLVR · Reinforcement Learning with Verifiable Rewards

让模型先采样回答，再由程序、测试或其他验证器判断是否满足目标，并利用奖励继续优化策略。

后训练数据量与数据类别

≈47B tokens

Instruct

倾向直接、遵循指令地回答。

≈167B tokens

Thinking

训练显式的思考过程与复杂问题求解行为。

两条数据线的混合都包括：聊天与指令遵循（chat & IF）、代码任务、Agent 轨迹、工具调用和错误恢复、推理以及安全。Agent 轨迹尤其重要：模型不只看最终正确答案，也会接触到调用工具、读取执行结果、修正错误并继续尝试的过程。

身份对话的过采样：错误会发生在看似简单的地方

早期模型有时会把自己介绍成 Google 助手。团队强调，合成数据流水线中没有 Google 模型；问题仍然发生。解决方法是将身份对话过采样 3 倍。这个例子体现了后训练里一个实际问题：即便来源没有使用某品牌模型，模型也可能从语料中的常见模式学到错误的身份描述，因此要用针对性数据纠正行为。

05 · REINFORCEMENT LEARNING

GRPO：为同一个问题采样一组答案，再用组内相对奖励更新策略

Mellum 的强化学习不只是选择一种目标函数。它还依赖大规模沙箱、专门的验证器、异步 rollout 与训练，以及处理不同推理引擎间概率差异的工程机制。

为什么代码任务适合 RLVR？

代码往往存在可执行的客观检查：运行单元测试、检查补丁、验证代码能否完成任务。这样奖励不必完全依赖人工偏好或另一个语言模型的主观评分。Mellum 的代码环境会按测试通过比例计分：即使一个补丁只修好一部分问题，也可以获得部分奖励，而不是只能拿到“全对 / 全错”的二元反馈。

GRPO 是什么？与 PPO 有什么关系？

GRPO（Group Relative Policy Optimization，组相对策略优化）由 DeepSeekMath 提出，是 PPO 的一种变体。PPO 通常需要一个价值模型（critic）估计当前状态未来能获得的回报，再用实际回报减去估计值形成 advantage。GRPO 的关键简化是：对于同一个 prompt，直接采样一组回答，以这组回答的奖励均值作为基线，比较每个回答相对于同组其他回答的表现，从而省掉单独训练的 critic。

1 · 采样同一个问题 q，由旧策略生成 G 个回答
→
2 · 验证运行测试、数学验证器或任务环境，得到每条回答的 reward
→
3 · 组内比较计算每条回答相对同组平均奖励的 advantage
→
4 · 更新策略用 PPO 风格的概率比率与 clipping 更新 token 概率

核心计算：奖励如何变成学习信号？

在原始 GRPO 的标准写法里，先计算组内平均奖励，再用奖励与组均值的差（通常还除以组内标准差）得到 advantage：

组内平均奖励μr = (1/G) Σi=1…G ri
标准 GRPO advantageAi = (ri − μr) / (σr + ε)
token 概率比ρi,t(θ) = πθ(oi,t | q, oi,<t) / πθold(oi,t | q, oi,<t)
PPO clipped termmin(ρA, clip(ρ, 1−ε, 1+ε)A) − β DKL(πθ || πref)

A 为 advantage；r 为验证器给出的奖励；πθ 是当前策略，πθold 是生成这组轨迹时的旧策略，πref 是参考策略。clipping 限制新旧策略在单次更新中偏离过大，KL 项则抑制当前策略离参考策略太远。

直觉是：同一个问题中，比其他回答得分高的回答会得到正向 advantage，该回答各 token 的概率会按这个信号被强化；比组内平均水平差的回答则会得到负向信号。使用同一 prompt 的分组比较，也减少了不同问题本身难度不同所带来的奖励尺度差异。

Mellum PPT 强调的 GRPO 配方细节

  1. 代码任务使用部分奖励：奖励等于通过的测试比例，所以部分修复仍有学习信号。
  2. 全组同分就丢弃：PPT 举例每组 16 个答案。如果它们的 reward 完全相同，组内没有谁优于谁的信号，无法形成有效的相对 advantage，因此跳过整组。
  3. 无法评分的答案给零奖励：如果回答格式或执行过程导致无法评分，先按零奖励处理，并把错误信息反馈进下一次 rollout，促使模型修正输出。
  4. 验证器崩溃与模型失败分开：如果是验证器基础设施故障，则重试，不计为模型零分，避免错误污染 reward 信号。
  5. 不按组内标准差缩放 advantage（Mellum PPT 的配方）：标准 GRPO 常把奖励差除以组内标准差；Mellum 幻灯片指出，这会过度放大“几乎解出来”与“几乎完全做不出来”的问题组。其配方不除以组内 spread，避免这类 prompt 被不成比例地加权。此处是 Mellum 所述的具体变体，不应误当成所有 GRPO 实现都采用相同做法。
  6. 按 token 聚合 loss：PPT 特别说 loss 按 token 平均而不是先把每条回答等权平均，避免长回答的 token 在整体训练中被低估。
  7. Instruct 与 Thinking 的 reward shaping 不同：Instruct 惩罚可见的思考过程，鼓励直接回答；Thinking 惩罚过长推理，以及跳过应使用工具的回答。

异步 rollout 为什么重要？

软件工程任务的轨迹长度差别很大：有的很快结束，有的要多次运行测试、读文件、改代码。如果同步循环等待一批里最慢的轨迹，GPU 训练端就会空转。Mellum 采用异步方案：vLLM 推理引擎持续生成 rollout，轨迹进入 buffer，Megatron-Bridge trainer 同时更新策略；更新权重推送到推理端后会重算 KV cache。

06 · TRAINING / INFERENCE MISMATCH

强化学习最怕奖励信号“看起来有用，实际却不对应同一个策略”

PPT 连续两页讲了训练与推理不一致，以及从标准 clipping 到 CISPO 的处理变化。这些属于训练系统工程，不只是 GRPO 公式本身。

训练引擎与推理引擎为何会算出不同概率？

rollout 通常由 vLLM 等推理引擎生成，而训练时会用 trainer 重新计算 token 概率。即便模型权重相同，批次大小改变也可能改变 GPU kernel 的浮点求和顺序，造成数值差异；MoE 模型还可能因为细微数值变化而把 token 路由到不同专家，再叠加 BF16 舍入误差。

PPT 引述的研究案例显示：相同权重下，vLLM 与训练器计算出的 token 概率可能出现极端差异。此时用训练概率除以 rollout 概率得到的 importance ratio，不一定代表正常的策略更新幅度，训练过程可能悄悄变成 off-policy。

Mellum 2.0 / 2.1 的处理：对 trainer / inference 概率比率落在 [0.5, 5.0] 之外的 token 做 mask，而不是 clip。PPT 的理由是：如果 MoE token 已经路由到不同专家，极端比率不再携带可靠的学习信号，直接裁剪数值反而会假装这个信号仍然可用。

从标准 clipping 到 clip-higher，再到 CISPO

方案怎么处理概率比PPT 指出的影响
标准 clippingratio 超出 [0.8, 1.2] 后，clipped objective 可能使该 token 没有有效梯度某些 token 被裁掉后不再学习。
2.0 · clip-higher只提高上界到 1.28放宽 ratio 上限，但仍采用 token 层面的 clipping。
2.1 · CISPO裁剪 importance weight，而不是直接裁掉 token每个 token 仍保留梯度；“wait”“recheck”等较少见 token 不会一触及边界就完全失去学习信号。

这里要区分两件事：前一页的 [0.5, 5.0] 是处理训练—推理引擎严重不一致的 mask 范围；后一页的 [0.8, 1.2] 与 1.28 是不同策略优化方案中的 clipping 设定。它们用途不同，不是同一条阈值规则。

Small SWE Agents 与 Jevons 悖论

Jevons 悖论指一种资源使用效率提高、单位成本降低后，总消费量反而上升的现象。放到 Agent 上，模型越便宜、响应越快，团队越可能把更多日常软件工程任务交给 Agent，因此系统效率会变得更重要。PPT 还提出开放问题：前沿模型是否已经能用很轻的工具脚手架（例如仅 bash）完成任务，而不必依赖复杂框架。
