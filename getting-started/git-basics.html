01心智模型：三棵树

先建立模型，后面所有命令都能自己推导出来。如果不理解三棵树，就只能死记命令，遇到报错完全无法判断。

1.1 三个位置

项目目录/                       ← 工作区 (working tree)
├── README.md                      你平时编辑的文件，操作系统直接可见
├── main.py
└── .git/                       ← 版本库 (repository)   Git 的全部家当
    ├── index                   ← 暂存区 (staging area)  单个文件，不是文件夹
    ├── HEAD                    ← 指针：我现在在哪个分支
    ├── objects/                ← 对象数据库：所有版本的内容，按哈希存放
    └── refs/heads/             ← 分支名 → 提交哈希 的映射
        └── main
常见误解：暂存区是 .git 文件夹

不少教程（包括某些纸质手册）会这么写，但不准确。暂存区的实体是 .git/index 这一个文件；.git 是版本库本体，.git/objects 只是其中的对象库。

1.2 文件的一生：四种状态

状态含义怎么进入git status 显示在哪
Untracked文件存在，但 Git 还没开始管它新建文件Untracked files
Modified已跟踪的文件被改了，改动还在工作区编辑已提交过的文件Changes not staged for commit
Staged改动已放到暂存区，下次提交会包含它git addChanges to be committed
Committed已经写进版本库，成为历史的一部分git commit不再出现（三者一致）
Untracked ──git add──→ Staged ──git commit──→ Committed │ （此后修改它就是） ↓ Modified

为什么新文件需要手动 add？ 因为 Git 只跟踪你亲手交上去的东西。如果 init 就自动纳入所有文件，凡是在大目录里误 init，几万个文件（包括几个 GB 的镜像、密钥文件）会瞬间被跟踪。

1.3 add 是"复制"，不是"搬"

git add 之后文件仍在工作区，只是暂存区里多了一份它的内容快照。这个区别很重要：

  • 因为是复制，所以 add 之后还能继续改文件，暂存区里保存的是 add 那一刻的内容
  • 此时 git status 会让同一个文件同时出现在 Changes to be committed（旧快照）和 Changes not staged（新改动）两个区块里——不是 bug，是"复制"模型的必然结果

1.4 提交是快照，不是补丁

每个提交保存的是当时整个项目的样子，不是"相对上一次改了什么"。差异是显示时现算的。

提交那一刻仓库里有
C1 添加 READMEREADME.md
C2 添加统计函数README.md + stats.py
C3 添加 utils上面两个 + utils.py

所以"C2 里没有 utils.py"是准确的说法——那时候它确实还不存在。git checkout C2 时 utils.py 会消失，正是因为它是"重构工作区去匹配 C2 的快照"。

1.5 指针链：HEAD → 分支 → 提交

HEAD ──→ main ──→ C3 ──→ C2 ──→ C1 ──→ (无)
  • HEAD 回答"我现在在哪"。它通常指向分支名，不直接指提交
  • 分支名（main）指向某个提交的哈希
  • 提交里存着"我的父提交是谁"的指针，于是链条一路回溯到根提交

可以直接读出这些指针——Git 没有任何数据库，全是一行行文本：

$ cat .git/HEAD
ref: refs/heads/main

$ cat .git/refs/heads/main
d9ff79d94cddbfa9f3e175317adbd69c53f68a10
为什么 HEAD 要间接指分支？

因为这样新提交时只需要移动分支指针，HEAD 始终钉在分支名上不动。切换分支时也只需改 HEAD 这一个小指针，所有提交一个不动——这就是"分支在 Git 里极其轻量"的根本原因。

提交之后指针怎么动：

提交前:  HEAD ──→ main ──→ C2 ──→ C1
提交后:  HEAD ──→ main ──→ C3 ──→ C2 ──→ C1
                     ↑
              main 前移一格，HEAD 不动

02安装与配置

2.1 安装

平台方式
Windowswinget install Microsoft.Git；或官网安装包；MSYS2 用户可直接装 mingw-w64-ucrt-x86_64-git
Ubuntu / Debiansudo apt install git
macOSbrew install git

装完验证：git --version。Windows 安装时务必勾选"添加到 PATH"，否则命令行里调不到 git。

Windows 上 winget 调不到时

常见原因是用户 PATH 里挂的是别人的 WindowsApps 目录（例如 C:\Users\Administrator\AppData\Local\Microsoft\WindowsApps），而真正的 winget 在 C:\Users\<你>\AppData\Local\Microsoft\WindowsApps。把 PATH 里那一条换成自己的即可。改完必须新开终端才生效。

2.2 身份配置（提交必须有）

git config --global user.name  "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main      # 新仓库默认分支用 main 而非 master
git config --global --list                       # 查看全局配置
  • --global 写进 ~/.gitconfig，对该用户所有仓库生效
  • 想给某个仓库单独设置：在该仓库目录下执行同样的命令但不写 --global
  • 邮箱会公开出现在每次提交记录里。不想暴露真实邮箱，可用 GitHub 提供的 xxxx@users.noreply.github.com

2.3 编辑器：git commit --amend / merge 时会弹出

编辑器保存并退出说明
nano（底部有 ^G ^X 提示）Ctrl+O → Enter → Ctrl+X最省事，什么都不用改
vimEsc → 输入 :wq → Enter左下角无菜单栏

换掉默认编辑器：

git config --global core.editor "code --wait"    # 用 VS Code
--wait 不能省

没有 --wait，VS Code 会立刻返回，Git 以为你编辑完了，于是用空信息提交。这是很常见的坑。

2.4 中文文件名显示成 \345\233\276...

git config --global core.quotepath false

只影响显示，不影响数据。默认值是 true，会把非 ASCII 字符转义。

2.5 SSH 密钥（推送到 GitHub 免密）

# 1. 先建目录（ssh-keygen 不会自动创建父目录）
mkdir ~/.ssh

# 2. 生成 ed25519 密钥对
ssh-keygen -t ed25519 -C "you@example.com" -f ~/.ssh/id_ed25519

# 3. 收紧权限（Windows）
icacls "$env:USERPROFILE\.ssh" /inheritance:r /grant:r "$($env:USERNAME):(OI)(CI)(F)"

# 4. 启动 ssh-agent（Windows 需管理员）
Set-Service ssh-agent -StartupType Automatic
Start-Service ssh-agent

# 5. 把私钥加载进 agent（没设口令短语则不会提示）
ssh-add ~/.ssh/id_ed25519
ssh-add -l

# 6. 复制公钥，粘到 GitHub → Settings → SSH and GPG keys
Get-Content ~/.ssh/id_ed25519.pub | Set-Clipboard

# 7. 测试
ssh -T git@github.com

公钥文件有三个字段，末尾那个只是备注标签，不参与认证：

ssh-ed25519  AAAAC3NzaC1lZDI1NTE5AAAAI...(base64)...  you@example.com
└── 算法 ──┘  └────── 真正的密钥本体 ──────┘  └─ comment ─┘

想改或删掉备注（例如不想公开邮箱）：

ssh-keygen -c -C "" -f ~/.ssh/id_ed25519      # 清空备注
ssh-keygen -c -C "win-home" -f ~/.ssh/id_ed25519
22 端口被网络屏蔽时

表现为 ssh -T 卡住几十秒后超时。改走 443：先验证 ssh -T -p 443 git@ssh.github.com，通了再写进 ~/.ssh/config：

Host github.com
  HostName ssh.github.com
  Port 443
  User git
  IdentityFile ~/.ssh/id_ed25519
口令短语的作用

私钥落盘后若无口令短语，文件就是"明文可用的钥匙"。设了口令短语 + ssh-agent 缓存，日常只需输一次。不确定自己设没设：ssh-add 时若没提示输入，说明是空口令，可用 ssh-keygen -p -f <私钥> 补上。

03日常最小闭环

git init                      # 在当前目录建仓库（只创建 .git/，不产生提交）
git status                    # 最重要的习惯：动手前先看状态
git add README.md             # 把文件放进暂存区
git status                    # 观察文件从 Untracked 移到 Changes to be committed
git commit -m "docs: 添加 README"
git log --oneline
命令真正做了什么
git init只创建 .git/ 目录。不改你的文件、不创建提交
git add <文件>把工作区内容复制进暂存区
git add .把当前目录下所有改动（新增+修改+删除）都放进暂存区
git commit -m "..."把暂存区打包成一个提交，写进版本库
撤销 git init

它的唯一产物是 .git/，所以直接删掉就还原了：rm -rf .git。练习仓库可以随便玩；真实项目慎用——这会抹掉全部提交历史。

3.1 提交信息的写法

推荐 Conventional Commits 约定，一眼看出这次改动的性质：

前缀用于
feat:新功能
fix:修 bug
docs:文档
refactor:重构（不改行为）
test:测试
chore:杂务（构建脚本、依赖、清理）

提交信息用双引号包起来。PowerShell 里若含 $，改用单引号避免变量展开：git commit -m 'fix: 修复 $HOME 的问题'。

3.2 git add 只能收编已存在的文件

$ git add test.py
fatal: pathspec 'test.py' did not match any files

这是"文件不存在"，跟分支毫无关系。顺序必须是先创建文件，再 add：

"print('hello')" | Set-Content test.py
git add test.py
git status

04查看历史与差异

4.1 git log 家族

git log                              # 完整：哈希、作者、日期、信息
git log --oneline                    # 紧凑：短哈希 + 信息
git log --oneline --decorate         # 带分支/标签名字（装饰）
git log --oneline --graph            # 用 ASCII 画分叉/汇合
git log --oneline --decorate --graph --all   # 最常用的一条
git log -p                           # 每次提交的完整 diff
git log --stat                       # 每次提交改了哪些文件
git log 是"新在上、旧在下"

输出按提交时间倒序排列。所以第一行是最新提交，最后一行是根提交。位置高低 ≠ 祖先关系——同一行里上下相邻的才是父子关系；不同分支的节点按时间穿插，可能出现"较新的提交反而排在下面某个节点之上/之下"的情况。

想看某个提交的父节点（判断是不是合并提交最快的方法）：

git log --all --graph --format="%h parents=[%p] refs=[%d] %s"
普通提交:  parents=[d9ff79d]                 ← 一个父
合并提交:  parents=[15a91d5 c140c3f]         ← 两个父

4.2 装饰（decoration）到底是什么

装饰 = 所有指向这个提交的引用名。--decorate 有三种档位：

写法效果
--decorate=short(HEAD -> main)、(feature)，省略 refs/heads/ 前缀；--decorate 等价于此
--decorate=full(HEAD -> refs/heads/main)，显示完整引用路径
--decorate=auto输出到终端才显示；被管道/重定向时不显示。未配置 log.decorate 时的默认值
--no-decorate强制关闭
为什么"加不加 --decorate 看起来一样"

因为默认是 auto，你在终端里跑时它已经自动显示了。只有把输出重定向到文件或管道给别的程序时，两者才有区别：

git log --oneline --graph > log.txt              # 不带装饰
git log --oneline --graph --decorate > log.txt   # 带装饰

想行为稳定不随输出目标变化：git config --global log.decorate short。

4.3 git diff：比的是哪两棵树

命令比较对象用途
git diff工作区 ↔ 暂存区看"改了但还没 add"的内容
git diff --staged暂存区 ↔ 版本库（HEAD）看"add 了但还没 commit"的内容
git diff HEAD工作区 ↔ 版本库看全部未提交改动
git diff <提交A> <提交B>两个提交之间跨版本比较
git diff <文件>限定单个文件减少噪音
add 之后 git diff 会变空

因为那时"工作区 == 暂存区"没有差异了。想看已暂存的内容必须用 git diff --staged。

读懂 diff 输出

diff --git a/stats.py b/stats.py          ← a/ 是旧版本，b/ 是新版本
index cde68d7..734a583 100644
--- a/stats.py
+++ b/stats.py
@@ -16,8 +16,14 @@ def minimum(numbers):     ← hunk 头：旧文件第16行起取8行，新文件第16行起取14行
     return min(numbers)                     ← 行首无符号：上下文行（两边相同）
 
+def total(numbers):                         ← 行首 +：新增
+    return sum(numbers)
-    return min(numbers)                     ← 行首 -：删除

git diff 与选项顺序

git diff 061ad11 README.md --stat
fatal: option '--stat' must come before non-option arguments
git diff --stat 061ad11 README.md          # 选项紧跟命令名
git diff --stat 061ad11 -- README.md       # 用 -- 分隔"引用"与"路径"，最稳

-- 之后的一切都当路径处理，不会误认成分支名。

4.4 只属于 A 的提交：A..B

git log --oneline main..feature      # feature 有、main 没有的提交
git log --oneline HEAD..origin/main  # 远程有、本地没有的提交

这是判断"这次合并会带进来什么"的最快方法。

05回退与撤销

先记住这一条

任何"丢弃改动"的操作，都先问自己一句：这些改动如果永远消失，我能接受吗？ 能接受才用丢弃类命令；不能接受就用 git stash。

关键区别：已提交的东西几乎都能救回来（reflog / 孤立提交）；从未提交的改动救不回来——它从来没进过 Git。

5.1 git restore：文件级别的撤销

命令作用丢东西吗
git restore <文件>把工作区文件还原成暂存区/版本库的版本丢未提交改动
git restore --staged <文件>把文件移出暂存区（工作区不动）不丢

它是 Git 2.23 从 checkout 里拆出来的新命令——因为老的 checkout 一个人干了太多互相冲突的事。

5.2 git stash：改动存进暂存栈

git stash                    # 把当前改动存起来，工作区回到上次提交的状态
git stash list               # 看栈里有什么
git stash pop                # 恢复并删除栈顶
git stash apply              # 恢复但保留栈顶
git stash drop               # 丢弃栈顶

典型场景：功能写到一半要紧急切分支修 bug。比 restore 安全，因为改动只是被挪走，没被销毁。

5.3 git reset：移动分支指针

reset 移动的是分支指针（HEAD 跟着走），三个档位决定要不要顺带清空暂存区和工作区：

命令分支指针暂存区工作区危险度
git reset --soft <提交>回退保留保留安全
git reset --mixed <提交>（默认）回退清空保留安全
git reset --hard <提交>回退清空丢弃危险
 
回退前:  HEAD ──→ main ──→ C3 ──→ C2 ──→ C1
回退后:  HEAD ──→ main ──→ C2 ──→ C1
                          ↑
                   C3 成了"孤立提交"（从树上摘下来，但还没被删除）
推荐 --mixed（默认）

它只动指针和暂存区，你的代码一个字节都不会丢，只是变成"改了但没 add"的状态，可以重新组织提交。

5.4 救回来：reflog 与孤立提交

git reflog                        # HEAD 的移动历史，每一步都在
git reset --hard HEAD@{1}         # 回到上一步

git fsck --lost-found             # 列出孤立提交/分支
git checkout <孤立提交哈希>       # 分离头模式进去看看
git branch rescue <孤立提交哈希>  # 把游离提交重新挂到分支上（救活）
git gc --prune=now                # 手动清理孤立提交

即使不手动 gc，孤立提交也会在约 90 天后被自动回收。

reflog 救不了什么

reflog 记录的是提交和指针的移动。--hard 销毁的未提交改动从未成为提交，reflog 里没有它——这是最容易造成真实损失的场景。

5.5 reset vs revert

resetrevert
本质改写历史（把时间倒回去）追加历史（记一笔"撤销"）
别人受影响吗会（历史变了）不会
适用还没推送、只有自己已推送、别人可能基于它开发
 
git revert <提交哈希>            # 生成一个反向提交来抵消它
git revert -m 1 <合并提交哈希>   # 撤销一个已被合并的 PR（-m 1 保留被合并分支的改动）

5.6 一句话决策

这个提交推送到远程了吗？ │ ┌────┴─────────────────────────┐ 没有 已经推送 / 别人在用 │ │ git reset（改写历史） git revert（追加历史）

06忽略文件

在仓库根目录建 .gitignore，一行一条规则：

# 目录
build/
__pycache__/

# 通配符
*.apk
*.pyc
preview_*.png

# 特定文件
debug.keystore
.env

# 例外（不要忽略这个）
!important.log
  • 不带斜杠的名字在任意层级都匹配：图片版/ 能匹配 a/图片版/ 和 a/b/图片版/
  • .gitignore 本身应该被跟踪
  • 空目录不会被 Git 跟踪——想保留目录就放个占位文件

6.1 已跟踪的文件不受 .gitignore 管辖

$ git add secret.env
The following paths are ignored by one of your .gitignore files:
secret.env
hint: Use -f if you really want to add them.

反过来：已经被提交过的文件，再加进 .gitignore 是无效的。必须先从 Git 里移除：

git rm --cached secret.env      # 从版本库移除，但保留工作区文件
echo "secret.env" >> .gitignore
git commit -m "chore: 停止跟踪 secret.env"

6.2 什么该忽略：产物 vs 源素材

核心判据：能不能由源码重新生成？能生成的不要进仓库。

文件进仓库？理由
源码（.java / .py / 资源 xml）✅ 必须真正的源
原始素材（设计图、照片）✅ 要没有它无法重新生成下游资源
构建产物（.apk / .class / .dex / build/）❌ 不要每次重建都是全新二进制，几 MB 起
密钥（.keystore / .env / 私钥）❌ 绝对不要泄露即事故
中间资源（压缩后的背景图）看情况若提交它能让构建不依赖额外工具链，就提交
二进制产物为什么不能进仓库
  • 无法 diff / merge：两个分支都改了就只能在整文件之间二选一
  • 无法复用：源码改一行，重新编译出的二进制整个都不同，Git 只能完整重存一份
  • 永久占空间：git rm 只是"以后不跟踪"，旧对象永远留在 .git/objects 里，克隆时照样下载
  • 要清理必须改写历史（filter-branch / BFG），会破坏所有人的本地仓库

正确做法：产物用 Releases 分发（见第 10 节）。

已经误提交了大文件怎么办

如果还没推送，最干脆的办法是删掉 .git 重建：

rm -rf .git
# 补好 .gitignore
git init && git add . && git commit -m "init"

一旦推送过，就不要再想"瘦身"了（除非能接受重写历史）。先检查再提交永远比事后补救便宜。

07分支

7.1 分支只是一个写着哈希的文件

$ cat .git/refs/heads/main
d9ff79d94cddbfa9f3e175317adbd69c53f68a10

这就是全部。所以创建、切换、删除分支都是瞬间完成的——不复制任何文件。

7.2 创建与切换

git branch feature              # 只创建，不切换（人还站在原分支）
git branch feature f865dc3      # 创建，并指定起点为某个提交
git branch feature main         # 创建，从 main 的当前位置分出
git checkout feature            # 切换
git checkout -b feature         # 创建 + 切换，一步到位
git checkout -b feature main    # 创建 + 切换 + 指定起点

git switch feature              # 新式写法（与 checkout 等价，职责更单一）
git branch -a                   # 本地 + 远程分支
git branch -vv                  # 带上游跟踪关系
git branch --merged             # 哪些分支已经被合并（删除前先看这个）
git branch 只创建、不切换

跑完 git branch feature 你还站在原分支上，必须再 checkout。这是最常见的困惑。

7.3 切换分支会改变工作区文件

checkout 不只是换指针，它还会把工作区改造成目标提交的样子：

情况Git 的行为
文件在目标提交里存在、当前也在 → 内容不同覆盖成目标版本
文件在目标提交里存在、当前没有创建出来
文件在当前分支已跟踪、目标提交里没有删除
文件从未被跟踪（Untracked）不动（不属于任何分支，Git 无权替你决定）

7.4 暂存区不随分支切换清空

.git/index 全局只有一个，不带任何分支标记。切分支时它原封不动带过去。

这会造成"提交进错分支"

在 A 分支 add 了改动、没提交就切到 B 分支，然后 commit——这个提交会落在 B 上。

纪律：commit 之前先看 git status 第一行的 On branch xxx。

而如果切换会覆盖你的暂存/未提交改动，Git 会拒绝：

error: Your local changes to the following files would be overwritten by checkout:
        utils.py
Please commit your changes or stash them before you switch branches.
Aborting

处理：git stash（想留）或 git restore <文件>（不要了）。

7.5 删除分支：-d 与 -D

git branch -d feature     # 安全删除：未完全合并就拒绝
git branch -D feature     # 强制删除：不管有没有合并
$ git branch -d feature
error: the branch 'feature' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D feature'

被拒绝说明该分支上有当前分支没有的提交。先想清楚再决定：

git log --oneline main..feature    # 看看到底有什么
git show <某个提交>                # 看具体内容
git merge feature                  # 想要就合并进来，然后 -d 就能删
git branch -D feature              # 确认不要了，强删

7.6 分离头模式（detached HEAD）

git checkout <提交哈希>     # 或 git checkout origin/main
# → You are in 'detached HEAD' state

此时 .git/HEAD 的内容从 ref: refs/heads/main 变成一串直接写的哈希：

正常:  HEAD ──→ main ──→ C2       (.git/HEAD 内容是 ref: refs/heads/main)
分离:  HEAD ──────────→ C2        (.git/HEAD 内容是一个提交哈希)
  • 可以查看任意提交的内容
  • 也可以提交，但没有分支指向新提交，切走后容易丢
  • 想保留就新建分支：git switch -c rescue
  • 想回去：git checkout main

08合并与冲突

8.1 先判断：这次会不会"真的合并"

Git 动手前先问一句："要合进来的分支，是不是我当前分支的祖先？"

判断结果行为会产生新节点吗可能冲突吗
是祖先（对方的一切我都有了）fast-forward：指针直接滑过去❌ 不会❌ 不可能
不是祖先（对方有我缺的东西）三方合并：真的合并内容✅ 产生合并提交⚠️ 可能
 
fast-forward 之前:              fast-forward 之后:
  main ──→ C2                     main    ──┐
              └──→ C3              feature ──┴──→ C3
  feature ─→ C3                   （两个标签重合了）

8.2 三方合并：Git 到底在合什么

        merge base（共同祖先）
             │
    ┌────────┴────────┐
    │                 │
 在 A 上改了什么     在 B 上改了什么
    │                 │
    └────────┬────────┘
             ↓
      把两边改动合成一份

不是"把 B 的子树搬过来"，而是"以共同祖先为基准，把两边的改动合在一起"。所以合并后两条线的成果共存。

合并提交有两个父：

d24c4ae parents=[15a91d5 c140c3f]
               └─父1      └─父2
        父1 = 你当时所在分支的尖端
        父2 = 被合进来的分支尖端

8.3 冲突的条件

冲突 = 两个条件同时满足

① 是真合并（不是 fast-forward）；② 两边改动了同一段内容且改法不同。

情况结果
两边改了不同文件✅ 自动合并
两边改了同一文件的不同区域（中间隔着足够多未改动行）✅ 自动合并
两边改了同一区域、改法不同💥 冲突
两边改了同一区域、改法相同✅ 自动接受
一边删文件、另一边改它💥 冲突
二进制文件两边都改💥 冲突（只能整文件二选一）

新手常高估冲突频率：大部分合并都是静默成功的，冲突只在"动到同一块地方"时才出现。

8.4 冲突长什么样

<<<<<<< HEAD
    return math.fsum(numbers) / len(numbers)     ← 当前分支（HEAD）的版本
=======
    return sum(numbers) / float(len(numbers))    ← 被合进来那一方（feature）的版本
>>>>>>> feature

记忆口诀：HEAD 在上面，被合进来的分支在下面。

为什么 Git 不自己选：两边都可能是"正确的改动"（一个为精度，一个为显式类型转换），选哪个取决于人的意图。Git 没有立场替你决定，所以把两个版本都写进文件。

8.5 解决冲突：四步

# 1. 看清现场
git status                     # Unmerged paths / both modified
git diff                       # 看冲突内容

# 2. 编辑文件：删掉 <<<<<<< ======= >>>>>>> 三行标记，
#    保留想要的内容（可以选 A、选 B，也可以融合成新写法）

# 3. 验证（这一步不能省！）
grep -n '<<<<<<<\|=======\|>>>>>>>' <文件>   # 应无输出
python <文件>                                    # 应能正常跑

# 4. 标记已解决并完成合并
git add <文件>            # 在冲突状态下，这条的含义是"我处理完了，请放行"
git merge --continue      # 或直接 git commit
git add 是"声明"，不是"解决"

Git 无法检查你是否真的解决了冲突。 git add 的唯一含义是"我声明这个文件处理好了"，Git 只能相信你。

所以：带着 <<<<<<< 标记 add 再 commit，那些标记会被永久写进仓库，文件也变成语法错误。git status 显示"All conflicts fixed"不代表真的修好了。

这也是团队用 pre-commit 钩子扫描冲突标记的原因。

合并相关命令

git merge --abort          # 只要还没 commit，一步还原到合并前
git checkout -m -- <文件>  # 把文件恢复成"冲突未解决"的原始状态
git merge --no-ff <分支>   # 即使能 fast-forward 也强制生成合并提交（保留分支痕迹）
git merge --squash <分支>  # 把对方的多个提交压缩成一个，不产生合并提交
git merge <分支> -m "..."  # 直接指定合并信息，不弹编辑器

8.6 "先合并进来再合回去"的四步法

git checkout feature
git merge main        # ← 冲突在这一步爆发，也在这里解决
git checkout main
git merge feature     # ← 此时是 fast-forward，不可能冲突
为什么第四步不会冲突

因为第二步完成后，main 的尖端已经是 feature 的祖先了，第四步退化为 fast-forward——没有内容需要合并，自然不可能冲突。

这不是"冲突被解决了"，而是"这一步无事可做，只挪指针"。

⚠️ 前提：如果第二到第四步之间 main 又动了，第四步就会变成真合并，冲突可能再次出现。

这个模式的真正价值：把冲突解决从网页编辑器搬到本地——能在 VS Code 里做三路对比，能跑测试验证，能看提交历史。

8.7 merge vs rebase

mergerebase
历史形状保留分叉，产生合并节点线性，像从未分叉
哈希原有提交不变全部重算（变基会改变提交哈希）
适合公共分支、需要保留真实历史本地私有分支、追求整洁线性历史
 
git rebase main                  # 把当前分支的提交"重放"到 main 顶端
git rebase -i <基点>             # 交互式：重排、squash、reword、drop
git rebase --continue            # 解完冲突继续
git rebase --abort               # 放弃
改写历史的铁律

不要 rebase 已经推送、别人可能基于它工作的提交。 变基会重写哈希，别人的历史就对不上了。已经公开的东西用 revert。

8.8 "区间内含分叉点"的报错

Cannot safely rewrite the source range — applying the rewrite would orphan refs
Interior fork(s) detected — every commit in the rewritten range (except the tip)
must have exactly one child within the range:
  - f865dc30: has 2 children (d9ff79d9, 15a91d5a)

原因：变基类操作要求重写区间是一条直线，但你把一个分叉点也圈进了区间——它有 2 个子提交。把它"摘下来重贴"会让原来的两条线失去父节点，产生历史碎片。

正确写法：用 ^ 把分叉点排除在区间外。

git rebase -i f865dc3          # ❌ 把分叉点也圈进来
git rebase -i f865dc3^         # ✅ 从分叉点的父开始，只圈它之后的
git rebase --onto main f865dc3 feature   # ✅ 明确指定起点与终点

这类报错常出现在 GitLens 的 Compose / 交互式变基这类"自动改写历史"的功能上——它对历史形状的要求比手动命令更严格。

09远程仓库

9.1 关联远程

git remote add origin git@github.com:USER/REPO.git   # 添加（origin 是习惯用的名字）
git remote -v                                        # 查看
git remote set-url origin <新地址>                    # 换地址（如 HTTPS ↔ SSH）
git remote remove origin                             # 移除

9.2 首次推送与上游跟踪（-u）

git push -u origin main

-u 是 --set-upstream，建立本地分支 → 远程分支的跟踪关系。之后就可以直接：

命令有跟踪关系没有跟踪关系
git push✅ 直接推当前分支❌ 要写 git push origin main
git pull✅ 直接拉❌ 要写全
git status✅ 显示领先/落后几个提交❌ 不显示

成功标志（会打印出来）：

branch 'main' set up to track 'origin/main'.

本地分支名和远程不一致时，用冒号指定：

git push -u origin master:main      # 把本地 master 推到远程 main

9.3 origin/main 是什么

它是本地的一个只读引用
  • 指向上次 fetch/push 时远程 main 的样子
  • 只在 fetch / push 时更新——别人刚推了代码而你没 fetch，你的 origin/main 就是过时的
  • checkout 到它会进入分离头模式
  • 别人推了新代码而你没 fetch → git status 也不知道你落后了

9.4 fetch vs pull

git pull  =  git fetch  +  git merge origin/main
命令做什么动工作区吗
git fetch只下载远程新提交，更新 origin/main❌ 不动
git merge origin/main把下载来的提交合并进当前分支✅ 会，可能冲突
git pull上面两步一次做完✅

更可控的写法（推荐）：

git fetch
git log --oneline HEAD..origin/main   # 先看看远程多了什么
git diff HEAD origin/main             # 再看看具体改了什么
git merge origin/main                 # 确认没问题再合并

9.5 push 被拒绝：non-fast-forward

! [rejected]        main -> main (fetch first)
error: failed to push some refs to 'git@github.com:...'
hint: Updates were rejected because the remote contains work that you do
hint: not have locally.

为什么会拒绝：远程有你没有的提交。Git 的原则是只允许在远程历史末尾追加，不允许覆盖——否则会删掉别人的工作。

正确处理：

git pull        # 拉下来合并（冲突在这里解决）
# 解完冲突：git add . → git commit
git push

错误处理：git push -f（会毁掉别人的提交）。

9.6 push 与冲突的关系（重要澄清）

push 永远不会产生冲突文件

冲突是 merge / rebase / pull 的产物，全是本地操作。push 只负责把已有提交传输到远程。

你的处境push 的结果
有未解决冲突、尚未提交Everything up-to-date，什么都不发生（没提交可推）
把冲突标记一起提交了推送成功，坏文件上网（事故）——push 不做内容检查
远程有你没有的提交被拒绝（fetch first），不产生冲突文件
解完冲突并提交后正常成功

一句话：冲突是本地的事，push 是传输的事。

9.7 强制推送

命令说明
git push -f / --force危险：无条件覆盖远程，可能丢失他人提交
git push --force-with-lease推荐：推送前检查远程有没有新提交，有就拒绝

9.8 同步状态：ahead / behind

## main...origin/main              ← 完全同步
## main...origin/main [ahead 1]    ← 本地多 1 个提交（该 push 了）
## main...origin/main [behind 2]   ← 远程多 2 个（该 pull 了）
## main...origin/main [ahead 1, behind 2]  ← 分叉了，需要合并
git rev-list --left-right --count main...origin/main
# 输出 "0  0" 表示两边一致；"1  2" 表示本地多 1、远程多 2

9.9 标签（tag）

标签是固定书签，标记发布里程碑。和分支不同，它不会随提交移动。

git tag v1.0                       # 轻量标签
git tag -a v1.0 -m "首个版本"       # 附注标签（推荐用于发布）
git tag -a v1.0 <提交哈希>         # 给特定提交打标签
git tag                            # 列出
git tag -d v1.0                    # 删除本地
git push --tags                    # 推送所有标签
git push origin --delete v1.0      # 删除远程标签
git push 不会推标签

标签必须显式 git push --tags。这是有意设计的：标签代表发布，不该跟着分支自动变动。

轻量标签 vs 附注标签

轻量 lightweight附注 annotated
创建git tag v1.0git tag -a v1.0 -m "..."
本质直接指向提交的引用一个独立的 Git 对象（含打标签人、时间、说明），再指向提交
git cat-file -tcommittag
ls-remote 显示1 行2 行
 
$ git ls-remote --tags origin
96faf9e...  refs/tags/v1.0        ← tag 对象本身
cf78e2b...  refs/tags/v1.0^{}     ← ^{} 是"剥离"语法：层层剥开直到露出提交

10GitHub 进阶：gh / Pages / Releases

10.1 GitHub CLI（gh）

# 登录：选 Login with a web browser，协议选 SSH，公钥已手动加过就 Skip
gh auth login
gh auth status
gh auth refresh -s delete_repo        # 追加某个 scope（不登出）

# 建仓库 + 关联 + 推送，一步完成
gh repo create myrepo --public --source . --remote origin --push

# 仓库改名（旧地址会重定向，Pages 地址不会）
gh repo rename newname --repo OWNER/oldname --yes

# PR 流程（全在本地完成，不开浏览器）
git checkout -b temp-branch
git commit -am "feat: xxx"
git push -u origin temp-branch
gh pr create --title "feat: xxx" --body "" --base main
gh pr merge --squash --delete-branch      # 或 --rebase
git checkout main && git pull && git branch -d temp-branch

gh config 在 gh auth login 时会自动设置 git_protocol=ssh，所以之后 gh 和 git 都走 SSH。

10.2 gh api：任何 GitHub 操作都能做

网页上的按钮 ≈ 一次 REST API 调用。gh api 就是直接调那个调用——所以没有按钮的功能也能通过它完成。

# 查询
gh api repos/OWNER/REPO
gh api "repos/OWNER/REPO/deployments?per_page=20"
gh api repos/OWNER/REPO/pages

# 修改（-X 指定方法，-f 传字段）
gh api -X POST repos/OWNER/REPO/pages -f "source[branch]=main" -f "source[path]=/"

# 删除（注意：有些资源要求先标记为 inactive）
gh api -X POST repos/OWNER/REPO/deployments/<id>/statuses -f state=inactive
gh api -X DELETE repos/OWNER/REPO/deployments/<id>
PowerShell 下 gh api 的两个坑

① 管道传 JSON 容易失败（报 Problems parsing JSON）。原因常是输入法把直引号换成了弯引号，或在 cmd 里单引号不被当作定界符。改用 -f "key=value" 完全绕开 JSON 字符串；嵌套用方括号 source[branch]=main。

② --jq 表达式含空格时会被 PowerShell 拆成多个参数。改用 ConvertFrom-Json 解析，或把表达式写成不含空格的形式。

10.3 GitHub Pages：把 HTML 变成网站

关键认知

仓库里的 HTML 不会"显示"，只会显示源码。 点开 .html 文件看到的是标签文本。要真正浏览网页，必须开启 Pages。

Pages 不是一个独立网站，而是仓库的一个属性。 地址由仓库名决定：https://<user>.github.io/<repo>/。改仓库名，地址跟着变；不存在"旧站点"需要删除。

开启方式（免费账号需要公开仓库）：

# 网页：Settings → Pages → Source: Deploy from a branch → main / (root) → Save

# 或命令行
gh api -X POST repos/OWNER/REPO/pages -f "source[branch]=main" -f "source[path]=/"

构建状态（异步，约 30–60 秒）：

gh api repos/OWNER/REPO/pages          # status: null → building → built / errored
gh api repos/OWNER/REPO/pages/builds/latest    # 失败时查原因

10.4 Pages 的项目结构约定

  • index.html 放根目录 → 访问 https://user.github.io/repo/ 直接打开它
  • 所有资源用相对路径 → 站点可整体移动到任意子目录而不需改链接
  • 推送后 Pages 会自动重新部署，不需要再进设置页
  • 中文文件名在 URL 里会被百分号编码，能用但不美观

10.5 Release：分发二进制产物的正确姿势

gh release create v1.0 app.apk --title "v1.0" --notes "首个版本"
塞进仓库走 Release
占 Git 历史✅ 永久占❌ 不占
下载方式要 clone 整个仓库点一下直接下
适合❌ 不适合✅ 二进制、安装包、数据集

10.6 改仓库名之后

类型旧地址
仓库地址 github.com/user/old永久重定向到新名（旧 clone/push 地址继续可用）
Pages 地址 user.github.io/old/直接 404，不重定向
Deployments 里的历史记录保留旧 URL 的卡片，可用 gh api 删除

想让旧链接不 404，可以建一个同名仓库，放一份纯跳转页：

<meta http-equiv="refresh" content="0;url=https://user.github.io/newname/">

10.7 其他开发笔记：不把密钥提交上去

误把 .env 提交了怎么办：

git rm --cached .env
echo ".env" >> .gitignore
git commit --amend --no-edit        # 如果还没推送、只错在最新一次提交

若更早的提交里也有，必须用交互式 rebase 或 filter-branch / BFG 清理历史。但无论如何都可能清理不干净——最可靠的动作是立刻轮换密钥 / 改密码。

附：学习路径建议

  1. 先立模型：三棵树 + 指针链（第 1 节）。不建立这个，后面全靠背。
  2. 走通最小闭环：init → status → add → commit → log，在一个空目录里反复做三遍。
  3. 学会读：git log --graph 和 git diff。这是"看懂状态"的能力，比会敲命令重要。
  4. 再动危险命令：reset 三档、restore、stash。练之前先 git branch backup。
  5. 分支与冲突：故意造一次冲突并解决。这是日常用得最多、也最容易卡住的环节。
  6. 接远程：push -u → 改代码 → push → 在网页上改一处 → pull，体会 ahead/behind。
  7. PR 流程：gh pr create / gh pr merge --squash，全本地完成。
  8. 静态站点：把一个 index.html 推上去、开 Pages、看到网页。
最高性价比的三个习惯
  1. 动手前先 git status，确认 On branch xxx 和当前状态
  2. 改历史前先 git branch backup-<日期>，成本 1 秒
  3. 不确定就 git stash，别 restore——前者能救，后者不能
